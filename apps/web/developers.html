MAZE DEVELOPER PLATFORM

Get paid in dollars, in one call.

MAZE turns any digital product or service into a checkout you can sell. Create an offer, share the link, and money lands in your balance. The same offers power a no-code payment link, a single REST call, and tools your AI agents can use directly.

Sourced values

Anywhere the API returns a number that came from a third-party provider — an APY, a swap quote, a market price, a freshly-issued IBAN — the response includes a sourced field. The shape is:

SourcedValueMeta
{
  "source":     "live" | "sandbox" | "cached-live" | "provider-demo" | "unavailable" | "error",
  "provider":   "Morpho",
  "fetchedAt":  "2026-06-17T15:42:18Z",
  "ttlSeconds": 30,
  "docsUrl":    "https://docs.morpho.org",
  "errorCode":  null,
  "errorMessage": null
}

The MAZE frontend renders this as a <nexa-source-badge> next to the value. Your integration can do the same, or hide the badge and only surface it on hover.

Overview

The MAZE API is organised around offers (a thing you sell for a price) and payments (a completed purchase of an offer). Create an offer and you get back a hosted checkoutUrl — sharing that link is the whole integration. Everything else (listing payments, reading your balance, reacting to events) builds on those two resources.

Base URL

All endpoints are versioned under /v1.

Base URL
https://api.maze.to/v1

# local development
http://localhost:8090/v1

Responses

  • A successful create or fetch returns the bare resource — no envelope.
  • Collections return { "object": "list", "data": [ … ] }.
  • Errors return { "error": { "type", "message" } } with a matching HTTP status.
  • Money is always US dollars; amounts in responses are strings like "9.99".
Error · 404
{
  "error": {
    "type": "invalid_request_error",
    "message": "No such offer."
  }
}

Authentication

Authenticate every request with your secret API key in the Authorization header as a bearer token. Create keys in the Developers section of the MAZE app — the raw secret is shown once at creation, so store it somewhere safe.

Authorization header
Authorization: Bearer sk_live_…

Live vs. test mode

Each key carries its mode in its prefix. sk_live_… moves real money; sk_test_… runs in sandbox mode against an isolated ledger with fake money, so you can build and replay the full flow without a single real charge. A test key only ever sees test offers, test payments, and the test balance.

PrefixModeMoney
sk_live_…liveReal dollars, real settlement
sk_test_…sandboxFake money, isolated ledger

Idempotency

To make a write safe to retry, send an Idempotency-Key header on your POST. If the same key arrives twice, MAZE returns the original resource instead of creating a duplicate — so a dropped connection or an automatic retry never charges or creates anything twice. Use a fresh unique value (a UUID is ideal) per logical operation.

Idempotency header
Idempotency-Key: 7f3b2c1a-9e44-4d2a-8b51-2a0d6c9e1f30

Sub-accounts

A sub-account is a separate balance under your single verified identity. Pass your KYC once, then open a sub-account per business, brand, or client you run — each keeps its own books while settling under the same key. Use them to separate proceeds, or as the destination when you split a sale.

Payouts

A payout sends money out of your balance to a developer, collaborator, or contractor. Each payout debits the balance of the key you present and, on success, fires a payout.completed webhook. If the amount exceeds your available balance, the call is rejected and no money moves.

Create a payout

POST /v1/payouts

destinationrequiredstringWho gets paid — an email or connected account handle.
methodenumHow to send it; defaults to your account's standard rail.
notestringOptional memo kept on the payout for your records.

Splitting a sale

When you create an offer, you can route its proceeds to a sub-account and carve off a cut for collaborators in the same call. Two optional fields on POST /v1/offers control it.

FieldTypeDescription
subAccountIdstringRoute the base proceeds to this sub-account's balance instead of your main one.
splitsarrayCuts to take off the top before the remainder lands in the base. Percentages must sum to 100 or less.

Each entry in splits names a recipient and a percentage of the sale:

FieldTypeDescription
subAccountIdstringCredit this sub-account's balance with the cut. Use this or email.
emailstringSend the cut as an automatic payout to this address. Use this or subAccountId.
percentrequirednumberThe recipient's share of the sale, e.g. 25.

A subAccountId split credits a balance; an email split becomes an automatic payout — so every email split also fires its own payout.completed webhook. Whatever the splits do not claim, the remainder, settles to the base (your main balance, or subAccountId if you set one).

Worked example — pay a clipper 25%

Sell a $20 offer and hand a quarter to the clipper who drove the sale. The clipper is paid $5 automatically and you keep $15.

Request · curl
curl https://api.maze.to/v1/offers \
  -H "Authorization: Bearer sk_live_…" \
  -H "Content-Type: application/json" \
  -d '{
    "title": "Founder OS course",
    "amountUsd": 20,
    "splits": [
      { "email": "clipper@x.com", "percent": 25 }
    ]
  }'

When a buyer pays the $20 at checkout, the money lands like this:

RecipientShareHow
clipper@x.com$5.00Automatic payout · fires payout.completed
You (base)$15.00Remainder, settled to your balance

Splits move real dollars for real work. The buyer pays a fiat price ("$20") for a genuine digital good or service, and each cut is a dollar payout to a real collaborator. This is never for in-game items or virtual currency.

Renew a subscription

POST /v1/subscriptions/:id/renew

Advance the subscription by one billing cycle. MAZE credits the seller with amountUsd, pushes currentPeriodEnd forward by a period, and fires a subscription.renewed webhook. MCP / agent tools

The third door. MAZE exposes its facilitator over the Model Context Protocol (Streamable HTTP, POST /mcp), so an AI agent can run the whole business — create the thing you sell, watch the sales land, and pay the crew — without a line of glue code. Same offers, same balance, same money as the no-code link and the REST call; just reached through tools the agent already knows how to use.

Connecting

Point your MCP client at /mcp and pass the agent's MAZE key. Present it in the X-Nexa-Key header, or as a bearer token in Authorization — either works. The key scopes the agent to exactly the offers, payments, and balance it is allowed to touch.

Endpoint
POST https://api.maze.to/mcp

# auth — either header works

Authorization: Bearer sk_live_…

Webhooks

Register an endpoint URL and MAZE will POST a signed event to it whenever something happens to one of your payments — so your system reacts the moment money moves, without polling. Registration returns a signing secret (whsec_…) once; store it to verify deliveries.

Verifying the signature

Each delivery carries a MAZE-Signature header of the form t=<unix>,v1=<hex>. The signature is an HMAC-SHA256, keyed with your endpoint's whsec_… secret, computed over the string `${t}.${rawBody}` — the timestamp, a literal dot, then the exact raw request body. Recompute it and compare; reject the request if it does not match (and optionally if t is too old).

Signature header
MAZE-Signature: t=1749808975,v1=4e2f…c0a1
Verify · Node
import { createHmac, timingSafeEqual } from 'node:crypto';

function verifyMazeSignature(rawBody, header, secret) {
  const parts = Object.fromEntries(
    header.split(',').map((kv) => kv.split('=')),
  );
  const expected = createHmac('sha256', secret)
    .update(`${parts.t}.${rawBody}`)
    .digest('hex');

  const a = Buffer.from(expected);
  const b = Buffer.from(parts.v1 ?? '');
  return a.length === b.length && timingSafeEqual(a, b);
}

// Express: use the RAW body, not the parsed JSON.
app.post('/maze/webhook', express.raw({ type: 'application/json' }), (req, res) => {
  const ok = verifyMazeSignature(
    req.body.toString('utf8'),
    req.header('MAZE-Signature') ?? '',
    process.env.MAZE_WEBHOOK_SECRET,
  );
  if (!ok) return res.status(400).send('bad signature');

  const event = JSON.parse(req.body.toString('utf8'));
  if (event.type === 'payment.paid') {
    // fulfil the order…
  }
  res.json({ received: true });
});

Sign over the raw request body, exactly as received. Parsing and re-serialising the JSON first will change the bytes and break verification.
